# Инструкции для Codex

## Язык и стиль общения

Общайся с пользователем только на русском языке. Объясняй нетривиальные решения простыми словами: проект учебный, пользователь изучает Ruby и Ruby on Rails.

Не переводи и не переименовывай названия файлов, классов, методов и переменных без необходимости.

## Проект

Это учебный проект игры «Тетрис» на Ruby on Rails 8, PostgreSQL, Inertia Rails, React, TypeScript, Vite и Tailwind CSS. Приложение развёрнуто на Render. Локально оно запускается командой:

```bash
bin/dev
```

Не изменяй настройки Render, Dockerfile, переменные окружения и конфигурацию деплоя без явного запроса. Локальный запуск сам по себе не подтверждает работоспособность на Render.

## Фактическая архитектура игры

### Rails

Основной контроллер — `app/controllers/games_controller.rb`.

В `GamesController` есть actions:

- `index`;
- `create`;
- `show`;
- `quit`;
- `finish`.

`GamesController` не содержит `step`. Маршрута для игрового шага также нет. Не добавляй его без явной необходимости и согласования: текущая игра не отправляет запрос на сервер для каждого движения.

Контроллер передаёт Inertia props `game_id` и `speed` странице `Games/Show`, а после завершения получает `speed`, `lines` и `duration` через `POST /games/:id/finish`.

### React и TypeScript

Текущая игровая механика выполняется в браузере. Её основной вход — `app/javascript/tetris/useTetrisGame.ts`.

Этот хук хранит состояние партии, запускает автоматический игровой тик, управляет ускоренным падением и анимацией очистки строк, а при game over отправляет итог на Rails.

Игровые модули находятся в `app/javascript/tetris/`:

- `game.ts` — состояние игры и операции шага, фиксации фигуры и очистки строк;
- `move.ts` — движение, падение и поворот;
- `figures.ts` — создание фигур;
- `collision.ts` — столкновения;
- `field.ts` — строки поля;
- `render.ts` — представление поля;
- `config.ts` — размеры и интервалы;
- `api.ts` — запрос сохранения результата.

Главная страница игры — `app/javascript/pages/Games/Show.tsx`. При изменении игрового поведения проверяй цепочку:

```text
React-компонент
        ↓
useTetrisGame и модули app/javascript/tetris
        ↓
запрос к Rails только для create / quit / finish
        ↓
GamesController и Inertia props
```

Не исправляй проблему только на одной стороне, если причина находится на другой. При изменении Inertia props убедись, что контроллер передаёт данные, а React их использует.

### Управление

Общее действие управления — `handleControl` из `useTetrisGame`. Оно используется и обработчиком физической клавиатуры, и мобильными кнопками. Поддерживаемые действия:

- `ArrowLeft` / ← — влево;
- `ArrowDown` / ↓ — ускоренное падение;
- `ArrowRight` / → — вправо;
- `ArrowUp` / ↑ — поворот;
- `Escape` — выход.

Не создавай отдельную игровую механику для нового способа ввода, если он может вызвать `handleControl`. При изменении управления проверь и клавиатуру, и `app/javascript/pages/Games/components/MobileGameControls.tsx`.

Мобильные кнопки находятся непосредственно под `GameField` и скрываются на ширине от `1024px` классом `lg:hidden`. Не удаляй и не ломай физическую клавиатуру без явной причины.

### Ruby-классы Tetris

В `app/services/tetris/` существуют `Tetris::Field`, `Tetris::Move` и `Tetris::Figure`, но текущая страница игры их не использует: активная реализация находится в TypeScript. Не считай эти Ruby-классы источником истины для работающей браузерной игры и не подключай их без отдельного анализа.

## Данные и база данных

Быстро изменяющееся состояние партии намеренно не хранится в базе: не добавляй в `games` положение фигуры, клетки поля, текущий тик или аналогичные данные.

Модель `Game` хранит запись игры и её итоговые данные (`speed`, `lines`, `duration`). Не изменяй модель, миграции или схему базы без необходимости. Если изменение базы действительно нужно:

1. объясни цель;
2. укажи таблицы и поля;
3. дождись согласия пользователя перед созданием миграции.

## Правила изменений

Перед существенным изменением:

1. изучи существующую реализацию;
2. найди связанные файлы;
3. установи причину проблемы или цель;
4. при неоднозначности предложи варианты и рекомендуемый путь;
5. изменяй только относящиеся к задаче файлы.

Не добавляй gems, npm-пакеты и не меняй технологии без явного согласия. Предпочитай небольшое изменение масштабному рефакторингу. Не исправляй молча найденные посторонние проблемы — сообщи о них отдельно.

## Проверка

Автоматические тесты в проекте пока не используются. Не добавляй тесты и тестовую инфраструктуру без явного запроса.

После изменений выполни доступные проверки:

1. изучи изменённые и связанные файлы;
2. проверь `git diff` и `git diff --check`;
3. запусти подходящие команды, например `npm run check`, `npm run build` или `bin/rails routes`;
4. если изменение связано с приложением, запусти `bin/dev` и проверь запуск Rails и Vite;
5. при возможности проверь сценарий в браузере.

Не утверждай, что работа проверена в браузере, если браузерная проверка не выполнялась. Отдельно указывай автоматические проверки, запуск приложения и действия, которые должен проверить пользователь.

## Git и безопасность

Перед существенными изменениями проверяй `git status`, после — `git diff`. Не создавай commit без явной команды пользователя. Не выполняй `git reset --hard`, опасные операции с Git и не удаляй незакоммиченные изменения пользователя без явного разрешения.
